# 向量记忆库召回实验方法手册

> 配套文章《搞不明白向量记忆库有什么用啊……》的实验附件。
> 数据来源：~1800 张日常记忆卡片（写代码、吃饭、聊天、情绪），60 对评估样本。

---

## 你的评估可能在骗你

一种常见的评估方式：让 LLM 读一张卡片的内容，生成一条查询，然后测这条查询能不能找回那张卡片。

这个方法有**同源偏置**——LLM 生成查询时自然会复用卡片里的关键词和表达，embedding 轻松找回。测的是"卡片→自身的向量一致性"，不是真实检索难度。

我用这个方法测出来 embedding@5 = 98%，以为召回没问题，于是砍掉了 reranker。

后来建了消除偏置的评估集（每条 query 独立标注多个期望卡片，不是"找自己"），hit rate 直接掉到 60%。**之前的 98% 完全不可信。**

### 怎么建不骗自己的评估集

1. **不要用卡片内容直接生成 query**——至少要转述、换说法、或从用户视角提问
2. **每条 query 标注多个期望卡片**——"关于吃饭的记忆"不应该只期望找到一张
3. **按卡片类型分层抽样**——事实、情感、偏好、承诺、计划的召回难度完全不同
4. **评估集规模 50-60 对起步**——太少的话按 type 拆分后每组样本不够

## 基线：关键词 vs 向量

评分公式：`base = kw × 0.5 + vec × 0.3 + importance × 0.2`，`final = base × vitality`

|  | 纯关键词 | 关键词 + 向量 |
|--|--|--|
| Hit Rate @5 | **60.0%** | 51.7% |
| Recall @5 | **0.206** | 0.178 |
| MRR | **0.476** | 0.319 |

**向量加进来效果反而下降。** 原因在正文里分析过：日常记忆内容高度同质，embedding 区分度不足（同类 avg 0.527 vs 异类 0.523），向量分量是噪声不是信号。

### 按卡片类型拆分——差异巨大

| 类型 | Hit Rate @5 | 说明 |
|--|--|--|
| plan（计划） | 100% | 关键词就够 |
| event（事件） | 100% | 关键词就够 |
| emotion（情绪） | 72.7% | 中等 |
| fact（事实） | 66.7% | 中等 |
| aggregate（聚合） | 50.0% | 关键词太泛 |
| preference（偏好） | 33.3% | 关键词脆弱 |
| promise（承诺） | 33.3% | 关键词脆弱 |

**不按 type 拆分，你看到的是 60% 的平均数；拆开一看，plan 是 100%，preference 是 33%。** 全局指标掩盖了结构性问题。

## 实验 1：Reranker 对不同类型的增益

粗筛 top-20 → reranker（BGE-reranker-v2-m3）精排 → 取 top-5。

### 整体

|  | 基线 | + reranker | 变化 |
|--|--|--|--|
| Hit Rate @5 | 60.0% | **63.3%** | +3.3% |
| Recall @5 | 0.206 | **0.267** | +29.6% |
| Precision @5 | 0.123 | **0.160** | +30.1% |
| MRR | 0.476 | **0.599** | +25.8% |
| Median Rank | 3 | **1** | 大幅改善 |
| 延迟 | 17ms | 1084ms | +62x |

### 按类型拆分

| 类型 | 基线 | + reranker | 判断 |
|--|--|--|--|
| fact | 66.7% | **100%** | 显著增益 |
| promise | 33.3% | **66.7%** | 翻倍 |
| event | 100% | 100% | 不变 |
| plan | 100% | 100% | 不变 |
| emotion | 72.7% | 72.7% | 不变 |
| preference | 33.3% | 33.3% | **无效** |
| aggregate | 50.0% | 37.5% | **有害** |

### 分析

- **fact / promise**：关键词能把卡片送进 top-20 粗筛池，reranker 读懂语义后精准提排。
- **preference**：rank 35-89，关键词碰不上，连粗筛池都进不去，reranker 无从精排。
- **aggregate**：reranker 被聚合卡片的泛化内容误导，把不相关的排上来，挤掉了原本靠关键词命中的结果。
- **plan / event**：关键词本来就精准，reranker 没有额外空间。

**结论：reranker 不是"有用"或"没用"，取决于卡片类型。** 之前我基于全局指标得出"召回侧不需要 reranker"的结论，是因为没按 type 拆开看。

## 实验 2：去掉向量 + 粗筛池大小

| 配置 | Hit Rate @5 | Recall @5 | MRR |
|--|--|--|--|
| 基线（无 reranker） | 60.0% | 0.206 | 0.476 |
| + reranker top-20 | **63.3%** | **0.267** | **0.599** |
| + reranker top-30 | 63.3% | 0.261 | 0.593 |
| 去向量 + reranker top-20 | 63.3% | 0.267 | 0.599 |

**发现：**
1. **去掉向量和保留向量结果一模一样**——再次证实向量是纯噪声
2. **放大粗筛池到 top-30 没有帮助**——preference 的 rank 是 35-89，top-30 还是捞不到
3. **当前最优配置**：`kw × 0.7 + importance × 0.3` 粗筛 top-20 → reranker 精排

## 还没解决的问题

### Preference 类型的 33.3%

这是最想让系统记住的东西——"你喜欢什么、你在意什么"——偏偏最难召回。

根因是关键词碰不上。比如卡片关键词是 `[情绪, 框架, 监控摄像头]`，query 关键词是 `[情绪, 喜好]`，只有"情绪"一个交集，而"情绪"太泛了，一堆卡片都有这个词。

可能的方向：
- **改关键词提取 prompt**：分层结构（领域词 + 实体词），禁止泛指词
- **改 query 侧**：召回时让 LLM 先扩展查询关键词
- **agent 检索**：搜一次不满意 → 自动改 query 再搜（用便宜模型，每轮 ~300ms）

### Aggregate 类型被 reranker 伤害

聚合卡片内容是多张卡片的综合摘要，语义模糊，reranker 容易被误导。可能需要对 aggregate 类型跳过 reranker，或在粗筛阶段给予额外权重。

## 实验方法清单

如果你也想测自己的记忆库，建议的实验顺序：

1. **建评估集**（最重要）：50-60 对，按类型分层，消除同源偏置
2. **跑基线**：纯关键词 / 关键词+向量 / 不同权重组合，按类型拆分看
3. **加 reranker**：粗筛 top-20 → reranker 精排，对比每种类型的增益
4. **诊断 MISS 样本**：导出未命中的样本，检查 query 和卡片的关键词交集
5. **改关键词**：在评估集上做 A/B 测试，不要直接改数据库

每一步都要**按卡片类型拆分看结果**。全局指标会骗你。

## 延迟参考

| 环节 | 耗时 |
|--|--|
| embedding 单次调用 | ~500-600ms |
| reranker 精排 20 条 | ~500-730ms |
| 含 reranker 的单次召回 | ~1.0-1.2s |
| 不含 reranker 的单次召回 | ~680ms |

1-2s 的延迟对对话场景可接受——人类也得想几秒怎么回。
